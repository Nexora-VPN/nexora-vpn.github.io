# مقصدهای بکاپ

پشتیبانی که فقط روی سرور پنل است، همراه همان سرور از دست می‌رود. مقصد بکاپ یک کپی از
هر فایل پشتیبان را جای دیگری می‌فرستد: فضای ذخیره‌سازی سازگار با S3، یک سرور SFTP یا
یک چت تلگرام. هر فایل پشتیبانی که پنل می‌نویسد، چه زمان‌بندی‌شده و چه دستی در
[[backup|تنظیمات ← پشتیبان‌گیری]]، در پس‌زمینه به هر مقصدی که روشن است می‌رود. این
صفحه زیر **سرویس‌ها ← مقصدهای بکاپ** است و مدیر اصلی راه‌اندازی‌اش می‌کند.

<NxShot page="backup-destinations" alt="صفحه‌ی مقصدهای بکاپ: سه کارت سرویس، برای فضای ذخیره‌سازی سازگار با S3، یک سرور SFTP و تلگرام" />

::: danger اول رمز بگذارید
فایل پشتیبان همه‌ی اطلاعات ورودی را دارد که این پنل دارد. بدون رمزگذاری، هر کس بتواند
یک مقصد را بخواند همه‌ی آن‌ها را دارد. پیش از روشن کردن یک مقصد، در
**تنظیمات ← پشتیبان‌گیری** یک رمز پشتیبان تعیین کنید؛ تا وقتی رمزی نیست، صفحه هشدار
می‌دهد.
:::

هر مقصد یک کارت است با **سرویس روشن**، تنظیماتش، **آزمایش** (که مقدار ذخیره‌شده را
امتحان می‌کند، پس اول ذخیره کنید) و **آخرین اجرا**. کلید یا رمز عبور پس از ذخیره دیگر
نمایش داده نمی‌شود؛ کادر خالی مقدار ذخیره‌شده را نگه می‌دارد.

## فضای ذخیره‌سازی سازگار با S3 {#s3-compatible-storage}

Cloudflare R2، AWS S3، Backblaze B2، MinIO و هر فضای ذخیره‌سازی دیگری که پروتکل S3
را می‌فهمد، از جمله object storage ارائه‌دهنده‌های محلی.

| تنظیم | |
| --- | --- |
| **نشانی سرویس** | آدرس فضای ذخیره‌سازی بدون باکت، مثل `https://<account>.r2.cloudflarestorage.com`، `https://s3.<region>.amazonaws.com`، `https://s3.<region>.backblazeb2.com` یا MinIO خودتان |
| **منطقه** | خالی = `us-east-1` که R2 و MinIO می‌پذیرند؛ AWS منطقه‌ی خود باکت را لازم دارد |
| **باکت** | باید از قبل وجود داشته باشد |
| **کلید دسترسی**، **کلید مخفی** | کلیدی که بتواند در آن باکت بنویسد، فهرست بگیرد و حذف کند |
| **پوشه** | پوشه‌ای درون باکت؛ خالی = ریشه‌ی آن |
| **نگه‌داری** | چند فایل پشتیبان آنجا نگه داشته شود (ببینید [نگه‌داری](#retention)) |

## SFTP {#sftp}

هر سروری که با SSH به آن می‌رسید.

| تنظیم | |
| --- | --- |
| **میزبان**، **پورت** | بدون scheme؛ پورت خالی یعنی ۲۲ |
| **نام کاربری** | |
| **رمز عبور**، **کلید خصوصی** | یکی یا هر دو؛ کلید به شکل PEM یا OpenSSH، بدون رمز |
| **کلید میزبان** | در اولین اتصال پر می‌شود و در هر اتصال بعدی بررسی می‌شود |
| **پوشه** | اگر نباشد ساخته می‌شود؛ خالی = پوشه‌ی خانه‌ی کاربر ورود |
| **نگه‌داری** | مثل S3 |

پنل بار اولی که وصل می‌شود به کلید میزبان سرور اعتماد می‌کند و پس از آن هر کلید دیگری
را رد می‌کند. اگر سرور از نو ساخته شده و کلیدش واقعاً عوض شده، **کلید میزبان** را
پاک کنید و ذخیره کنید؛ اتصال بعدی کلید تازه را ثبت می‌کند.

فایل پشتیبان با یک نام موقت نوشته می‌شود و وقتی کامل شد تغییر نام می‌دهد، پس فایلی که
نیمه‌کاره بارگذاری شده هرگز شبیه یک پشتیبان نیست.

## تلگرام {#telegram}

فایل پشتیبان به شکل یک فایل در یک چت می‌رسد، که بات
[[telegram|سرویس تلگرام]] آن را از راه پراکسی همان سرویس می‌فرستد، پس اول آن سرویس را
راه‌اندازی کنید.

| تنظیم | |
| --- | --- |
| **شناسهٔ چت** | چتی که با یک حساب مدیر اصلی جفت شده، با عددی که صفحه‌ی تلگرام زیرش نشان می‌دهد |

این چت می‌تواند چت خصوصی شما یا گروهی باشد که با شما جفت شده. در گروه همه‌ی اعضا فایل
پشتیبان را می‌گیرند، و همراهش همه‌ی اطلاعات ورودی که پنل دارد، پس گروه را با در نظر
گرفتن همین انتخاب کنید.

Bot API فایل‌هایی تا **۵۰ مگابایت** را می‌پذیرد. فایل بزرگ‌تر به‌جای اینکه فرستاده شود
و شکست بخورد، با همین دلیل رد می‌شود؛ برای پنلی که پشتیبان‌هایش بزرگ‌ترند از S3 یا
SFTP استفاده کنید. هیچ چیزی در چت حذف نمی‌شود، پس **نگه‌داری** اینجا اعمال نمی‌شود.

### فایل‌های افزونه‌ها {#addons-files}

تا وقتی این مقصد روشن است، یک افزونه، یا اسکریپتی از خودتان، که دسترسی
`backup:deliver` را دارد می‌تواند فایل خودش را به همان چت بفرستد. پنل آن را بدون نگه
داشتن منتقل می‌کند، با توضیحی شامل نام فرستنده، نام فایل و حجمش: تا ۵۰ مگابایت و شش
فایل در ساعت برای هر فرستنده. افزونه این دسترسی را با دلیلش در صفحه‌ی رضایت درخواست
می‌کند (ببینید [[use/addons]])؛ خاموش کردن مقصد همه‌ی این ارسال‌ها را متوقف می‌کند.

## نگه‌داری {#retention}

**نگه‌داری** تعداد فایل‌های پشتیبانی است که یک مقصد نگه می‌دارد. خالی از مدت
نگه‌داری تنظیم‌شده در صفحه‌ی پشتیبان‌گیری استفاده می‌کند؛ `0` همه را نگه می‌دارد. پس
از هر بارگذاری، قدیمی‌ترین فایل‌های بیش از آن تعداد از مقصد حذف می‌شوند.

فقط فایل‌هایی حذف می‌شوند که نامشان مثل فایل‌های پشتیبان پنل است، پس همان باکت یا
پوشه می‌تواند چیزهای دیگری هم داشته باشد.

## وقتی بارگذاری شکست می‌خورد {#when-an-upload-fails}

بارگذاری ناموفق هرگز پشتیبان‌گیری را ناموفق نمی‌کند:

- فایل پشتیبان روی سرور پنل می‌ماند؛
- **آخرین اجرا**ی مقصد خطا را نشان می‌دهد؛
- رویداد `panel.backup_upload_failed` به تلگرام، ایمیل و هر وب‌هوکی که به آن گوش
  می‌دهد فرستاده می‌شود (ببینید [[webhooks]])؛
- فایل پشتیبان بعدی طبق معمول دوباره فرستاده می‌شود.

مراقب این رویداد باشید، یا هر از گاهی **آخرین اجرا** را نگاه کنید: مقصدی که یک ماه
بی‌صدا شکست بخورد یعنی یک ماه پشتیبانی که ندارید.
